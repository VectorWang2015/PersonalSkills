# 重新蒸馏、匿名比较与合并

## 目标

在不受旧实现锚定的前提下，从原书重新得到一份独立候选解；冻结后再与旧 skill 对齐，通过 old/new/no-skill 匿名比较判断哪些设计真正有用，最后只合并有证据支持的优点。

## 核心顺序

```text
定义范围并隔离旧资产
  → 只看原书的独立蒸馏
  → 冻结独立实现
  → 在不解冻实现的前提下做 new/no-skill holdout
  → 首次打开旧 skill / 旧测试 / 旧评审
  → 能力对齐与匿名 old/new/no-skill 评测
  → 逐项选择和合并
  → 用新 holdout 复测 merged
  → 保留旧版后交付
```

任何先读旧 skill 再“独立重做”的流程都不是盲态重蒸馏。

## 0. 预注册范围

在隔离旧内容前记录：

- 原书版本、来源指纹和本轮可用范围；
- 用户目标、目标受众、运行环境和授权边界；
- 计划使用的当前 book2skill 方法论版本；
- 盲态执行者可见与不可见的资产类别；
- 冻结条件、比较维度和交付门槛；
- 无法实现完全隔离的已知限制。

可以由协调者记录旧目录位置和内容指纹以便以后核对，但不要把文件正文、测试名称、slug、旧总结或评审结论交给盲态蒸馏者。

## 1. 盲态独立蒸馏

盲态执行者只能收到：

- 原始书本文本和必要的版本元数据；
- 用户本轮明确的目标与范围；
- 当前方法论和目标运行环境的通用约束；
- 完成本轮所需但不包含旧解信息的工具。

明确禁止：

- 读取旧 SKILL.md、references、scripts、assets 或 INDEX；
- 读取旧 test prompts、评测结果、issue、提交说明或改进建议；
- 从旧目录名和 slug 推断应提取哪些能力；
- 让了解旧实现的评审者向执行者暗示缺陷或期望答案。

盲态实现者完成独立来源建档、提取、验证、promotion、构造和 dev 回归。Holdout 由未参与最终编辑、只对版本身份盲态的独立评测角色或隔离过程预先冻结；来源忠实度评审仍可查看原书。实现者不应看到具体答案后再改同一版本。若实际平台无法保证上下文隔离，应如实标记为“有限盲态”，不能声称完全独立。

## 2. 冻结独立结果

在查看任何旧资产之前先冻结独立实现：

- 生成的 skills、支持资源和 candidate lineage；
- 来源清单、覆盖地图和证据账本；
- promotion 记录与被拒绝候选；
- dev 数据集、实现者未见的 holdout 标识及其隔离记录；
- 内容指纹、时间、方法论版本和执行环境；
- 未解决问题及 holdout 前的 provisional recommendation；最终发布状态留待独立评测。

冻结后不再静默修改 new。先在保持实现冻结的前提下运行 new-vs-no-skill holdout，并把结果加入 freeze manifest，再依据证据给出本版本的 release status。若必须根据失败修改，则创建新的独立 revision；已查看的样例转为 dev，并以新 holdout 重新评测和冻结。后续发现的问题通过新版本或 merge 分支处理，以便比较者看到真正独立的结果。

## 3. 冻结后能力对齐

此时才允许读取旧资产。先按“完成的用户任务”建立映射，而不是按文件名或章节名匹配：

| 对齐关系 | 含义 |
|---|---|
| one-to-one | old 与 new 处理同一能力 |
| one-to-many | 旧能力被 new 合理拆分，或反之 |
| old-only | 旧版有独立能力，新版漏掉或主动拒绝 |
| new-only | 新版发现旧版没有的能力 |
| support-only | 某一方把内容作为 reference，而另一方做成独立 skill |
| conflict | 两方对来源含义、触发条件或步骤有实质分歧 |

对每项记录来源 fidelity、执行契约、路由、支持资源、脚本和评测覆盖差异。不要先决定“新版一定更好”。

## 4. 匿名 old/new/no-skill 比较

遵守 `06-stage4-pressure-test.md`：

- 把 old、new、no-skill 随机映射为无语义标签；
- 使用相同任务、模型、工具、权限和上下文；
- 评分者先看冻结 rubric，不知道版本身份；
- 同时运行来源忠实度、任务完成度、路由和机械断言；
- 使用独立 holdout，不把旧版或新版自己调优过的测试作为唯一依据。

比较应回答：

- 哪一版在哪类任务上产生了可重复的实际增益？
- 优势来自哪条具体规则、契约、脚本或边界？
- 是否有版本只增加篇幅、术语或仪式感，却不优于 no-skill？
- 哪些失败是来源误读，哪些是路由、执行或包装问题？

## 5. 逐项合并

合并单位是可归因设计，而不是整套文本。可以分别选择：

- 更忠实的 claim 和证据锚点；
- 更清晰的 trigger、输入、输出和停止条件；
- 更可靠的步骤、公式或确定性脚本；
- 更有区分力的兄弟路由和负例；
- 更有效的渐进披露结构；
- 更真实的限制、时效和风险说明。

每项保留选择理由和来源 lineage。不要把 old 与 new 全文相加；重复规则、冲突步骤和过长入口会降低性能。旧版的独有内容若没有来源或评测支持，可以保留为待核对候选，而不是因“历史上存在”自动进入 merged。

## 6. 重新评测 merged

Merged 是新的实现，不能继承 old 或 new 的分数。必须：

- 回归双方关键 dev cases；
- 运行双方未泄漏的兼容 holdout；
- 增加一组未用于合并决策的新 holdout；
- 重跑兄弟路由诱饵和机械断言；
- 与 old、new、no-skill 做必要的匿名比较；
- 检查上下文长度、复杂度和依赖是否因合并显著回退。

查看某个 holdout 失败并修改 merged 后，该样例转为 dev；继续声称泛化时需要新的 holdout。

## 7. 交付与保留

- 在 merged 达到预注册门槛前不要覆盖 old；
- 保存 blind freeze manifest、对齐表、匿名结果和 merge decision log；
- 对未解决的 old-only / new-only 能力给出保留、延后或拒绝理由；
- 标明本轮盲态强度和任何泄漏；
- 按 `07-stage5-deliver.md` 交付，安装、发布或远程同步仍需原任务授权。

## 常见失真

- 独立蒸馏者提前看到旧目录、旧测试或“上次哪里不好”的提示；
- 冻结只是口头声明，比较期间直接改写 new；
- 用旧版测试证明旧版更好，或用新版测试证明新版更好；
- 只比较文档完整度，不运行 no-skill 基线和真实任务；
- 把两版并集当成“取长补短”，导致入口膨胀和规则冲突；
- 只保留新版发现，忽略旧版在特定任务上可归因的优势；
- 合并后没有新 holdout，却沿用两边最佳分数。
