# 阶段 3 — Portfolio 结构与兄弟路由

## 目标

让多个 skills 形成可理解、可发现且不互相争抢的能力组合。链接只在会改变路由、执行顺序或信息加载时存在；不为模仿卡片盒形式而制造关系图。

## 先做能力清单

对每个拟发布 skill 记录：

- 用户要完成的任务；
- 正向 trigger 与关键排除条件；
- 必需输入和交付物；
- 风险、权限和时效等级；
- 依赖的共享资源；
- 来源 candidate IDs；
- 最相近的兄弟 skill。

如果两项能力无法从这张清单中区分，返回 promotion gate 合并或重划边界，不靠更长的说明掩盖冲突。

## 只使用有操作意义的关系

- `depends-on`：A 在执行前确实需要 B 的产物或判断；
- `contrasts-with`：A 与 B 处理相近请求，但选择条件不同；
- `composes-with`：A 与 B 可独立使用，在某些任务中组合能提高结果；
- `routes-to`：A 识别到特定条件后应把任务交给 B；
- `supersedes`：新版本明确替代旧能力，同时保留回滚和 lineage。

关系应写明“何时以及为什么”，不只列 slug。若依赖形成环，检查是否应该合并、抽出共享组件，或把关系改成可选组合。

## 兄弟路由矩阵

对 trigger 接近的 skills 建立最小对照表：

| 用户任务特征 | 首选 skill | 不选兄弟 skill 的原因 | 转交条件 |
|---|---|---|---|
| 已有方案，需要找致命失败路径 | inversion-review | 不是从零生成方案 | 若需要概率和损失量化，转 quantitative-risk |
| 有多个带概率结果的方案 | quantitative-risk | 需要数值比较，不只是反向审查 | 数据不足时先做信息缺口分析 |

该矩阵有两个用途：

1. 精炼每个入口的 description 和边界；
2. 为阶段 4 生成“兄弟路由诱饵”：表面高度相关，但正确答案应是另一个 skill 或不加载任何 skill。

不需要为完全不相似的 skills 做两两比较。

## 渐进披露检查

Portfolio 结构也承担资源路由：

- 每个 reference 或 script 至少有一个明确消费者；
- 入口说明什么条件下读取哪个支持文件；
- 共享资源只在确有多个消费者且语义一致时抽取；
- 领域或法域细节不默认加载给无关任务；
- INDEX 或 manifest 提供能力导航，不复制每个 SKILL.md 的完整内容。

## INDEX / manifest 应回答什么

Canonical capability bundle 是关系与 promotion 状态的事实源；INDEX 是由它生成或同步维护的导航视图，不应反过来覆盖 card 中的契约。格式可按项目约定，但至少应让维护者找到：

- 每个 skill 的能力、trigger 和交付物；
- 必要的依赖、对比、组合和替代关系；
- 来源 lineage 和版本；
- 共享资源的消费者；
- 高风险或实验性状态；
- 推荐的基本调用顺序（仅在真实依赖存在时）。

图表只有在关系多到文字难以理解时才使用。不要规定固定关系数量；一个结构良好的 portfolio 可以很稀疏。

## 评测种子

在本阶段为每组兄弟能力至少提出有区分力的任务族：

- 明确属于 A 的任务；
- 明确属于 B 的任务；
- 两者都不应触发的表面诱饵；
- 需要先 A 后 B、或只组合一次的任务；
- 信息不足，应询问而非任选一个 skill 的任务。

这些只是测试设计输入。正式 holdout 必须由未参与最终编辑的人或独立过程冻结，不能把所有诱饵都暴露给实现者后仍称为 holdout。

## 完成条件

- 每个关系都会改变路由、执行或按需加载；
- trigger 冲突已通过合并、重划边界或明确转交解决；
- 没有孤立且无人引用的支持资源；
- 已识别最危险的兄弟路由诱饵；
- portfolio 信息没有与各 skill 入口形成难以维护的重复正文。
