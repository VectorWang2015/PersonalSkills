# 阶段 4 — 独立行为评测

## 目标

验证 skill 是否在真实任务中正确路由、遵守执行契约并产生实际增益。评测关注可观察行为，不以标题、固定措辞、章节齐全或自报“已使用方法”为成功。

## 评测臂

### 新蒸馏

至少比较：

- `new-skill`：加载待测 skill；
- `no-skill`：在相同模型、工具、上下文和权限下不加载该 skill。

### 重蒸馏

冻结独立新结果后，在相同条件下比较：

- `old-skill`；
- `new-skill`；
- `no-skill`。

合并版本完成后再增加 `merged-skill`。不要用旧版本自己编写且已经调优过的测试作为唯一评测集。

## 匿名与隔离

- 将各评测臂随机映射为 A/B/C 等无语义标签，执行者和评分者不应从路径、提示或输出标题知道版本身份；
- 以随机顺序运行，避免固定顺序和缓存造成偏差；
- 除加载的 skill 外，模型版本、系统约束、工具、用户任务、温度或其他采样设置应尽量一致；
- 评分 rubric 在查看输出前冻结；
- 来源忠实度评审可以查看原始来源，但不能知道输出来自 old/new/no-skill；
- 若资源允许，让设计者、执行者与评分者分离；做不到时记录限制并降低结论置信度。

匿名比较不是安全隔离。若模型或评审者能从措辞猜出版本，应记录可能的泄漏，不把盲评表述得比实际更强。

## 数据集分层

### Dev 集

用于设计和修正，可以被实现者查看。覆盖：

- 应触发的典型任务；
- 明确不应触发的任务；
- 边界模糊任务；
- 缺少必需输入、需要询问或停止的任务；
- 高风险权限或时效条件。

### Holdout 集

在最终编辑前由独立评测者或隔离过程冻结。实现者不得根据 holdout 的具体答案改 skill 后仍重复声明它是未见数据。若查看失败样例并据此修改，相关样例转为 dev；需要补充新的 holdout 才能再次估计泛化。

Holdout 应来自与真实用户任务相同的分布，但不能只是 dev prompt 的同义改写。

### 兄弟路由诱饵

为 trigger 接近的每对能力设计：

- 表面含有本 skill 关键词，但实际应路由到兄弟 skill 的任务；
- 两者都相关，但应先询问缺失信息的任务；
- 两者都不应加载的低价值或纯信息任务；
- 需要组合时能够观察调用顺序的任务。

这类测试检查的是选择能力，而不是让所有 skills 都输出一个答案。

## 机械输出断言

将确定性要求与主观质量评分分开。适合机械检查的断言包括：

- 必需字段、文件或 schema 存在且可解析；
- 输出引用的 candidate ID、来源锚点或数据列确实存在；
- 数值公式、单位、符号、舍入和总分关系可复算；
- 必须包含的风险、假设、as-of 日期或停止状态已出现；
- 禁止的外部操作、越权写入或无依据断言没有发生；
- 当输入缺失时，输出为询问或明确无法计算，而不是编造值；
- 路由结果只能是允许集合中的一个，组合顺序符合依赖。

不要对自然语言正文做整段精确匹配，也不要把“出现某关键词”当作完成真实任务的替代指标。关键安全、权限、数据完整性和数学一致性断言可以设为必须通过。

## 评分维度

使用与任务匹配的 rubric，通常包括：

- 任务是否真正完成，答案是否正确；
- 是否忠实使用来源，而没有把推断冒充原书；
- 是否比 no-skill 找到更多会改变行动的有效信息；
- 路由是否精准，是否克制地不触发；
- 是否满足输出契约和机械断言；
- 是否遵守权限、时效、风险和停止条件；
- 额外上下文、延迟和复杂度是否与增益相称。

自由文本质量可由匿名评分者做成对比较，并记录选择理由与置信度。不要只汇总一个通过率而丢失关键失败类型。

## 实际增益判定

新 skill 应在目标任务族上相对 no-skill 展现可重复且有意义的改善，同时没有不可接受的路由、安全或成本回退。重蒸馏版本还应与 old-skill 比较：

- 若 new 在关键任务上胜出且没有重大回退，可作为合并基底；
- 若 old 在某些任务明显更好，提取其可归因优势，而不是整体复制；
- 若两者都不优于 no-skill，应重新审视是否需要该 skill；
- 若差异小于评测噪声，结论应是“尚无充分证据”，而不是宣布升级成功。

不设置适用于所有书的固定通过率。样本量、风险和失败代价不同，发布阈值应在测试前确定。关键错误即使总分高也不能被平均掉。

## 运行流程

1. 从 promotion 记录和兄弟路由矩阵定义能力声明与失败代价；
2. 冻结 rubric、dev/holdout 划分、机械断言和评测臂；
3. 对评测臂匿名化并随机运行；
4. 先执行机械断言，再做来源核对和匿名质量比较；
5. 按任务族、路由类型和风险层分解结果；
6. 将失败归因到路由、输入契约、过程、来源、边界、工具或测试设计；
7. 只针对有证据的失败修改 skill；
8. 用 dev 回归并以未泄漏 holdout 复测。

## 测试修订纪律

- 测试与用户真实目标不一致时可以修，但必须记录理由和版本；
- 不能因为 skill 失败就把合理 holdout 改成容易通过；
- 新发现的合理使用场景应先决定是扩展范围还是明确排除，再补测试；
- 每次修订保留历史结果，防止修复一个任务族却破坏另一个；
- 重蒸馏比较在 blind freeze 之后进行，不能提前把旧测试答案喂给新蒸馏者。

## 产物

格式可按项目工具调整，但应保留：

- 数据集版本、来源与 dev/holdout 标记；
- 匿名映射的受控记录；
- 模型、工具、权限和运行设置；
- 每个输出、机械断言和评分理由；
- old/new/no-skill（以及 merged）的分任务比较；
- 已知泄漏、噪声和限制；
- 发布建议：`ready`、`pilot`、`revise` 或 `reject`。
