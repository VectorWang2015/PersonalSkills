# 阶段 5 — 验证与交付

## 目标

交付一个范围清楚、可安装或可复用、可审计且可回滚的 skill 包。交付不是把内部候选全部打包，也不是自动获得安装、发布或覆盖旧版本的权限。

## 发布状态

在交付前明确选择：

- `ready`：关键质量门和目标 holdout 均满足，可作为当前推荐版本；
- `pilot`：核心能力可用，但样本、平台或边界仍需受控试用；
- `revise`：存在可修复缺口，不应宣称完成；
- `reject`：没有可证明增益，或来源、风险问题使其不宜发布。

状态必须与阶段 4 的证据一致。不要把“文件已经生成”当成 ready。

## 包完整性检查

- 必需入口存在，名称和 description 与能力边界一致；
- 入口链接的 references、scripts、assets 都存在，反向也有明确消费者；
- 没有模板占位符、失效链接、重复规则或无人读取的文件；
- frontmatter、JSON、YAML 或其他结构化文件能被目标环境解析；
- 新增或修改的确定性脚本通过实际运行测试；
- 机械输出断言和关键安全断言通过；
- 支持的目标平台、依赖和已知限制有明确记录；
- 未把本地路径、特定代理名称或不可用工具写成普遍前提。

若目标环境提供 skill 校验器，应运行它，但校验器通过只代表包装格式基本正确，不代表行为有效。

## 来源与 lineage 检查

交付清单应能回答：

- 这个 skill 来自哪些 candidate IDs 和原书版本？
- 哪些规则是作者明确主张、综合结论或蒸馏者推断？
- 证据账本在哪里，关键锚点是否仍可解析？
- 是否有 OCR、译本、缺页、时效或法域问题？
- 重蒸馏时，它与 old/new/merged 哪个版本对应，盲态冻结清单在哪里？

避免交付不必要的长篇版权文本。引用只保留核对所需片段；不能再分发的来源只记录用户可用的定位信息，不复制全文。

工作态 source manifest 可以保存本机绝对路径用于复现，但发布包只能包含净化副本：

- 设置 `local_paths_redacted: true`；
- 将顶层 `base_directory` 置为 `null`；
- 将每个 source 的 `absolute_path` 置为 `null`；
- 检查其他 manifest、报告、日志和生成文件，不得泄露 home、workspace、临时目录或用户特定挂载路径；
- 保留不敏感的 `source_id`、内容指纹、版本、相对定位规则和必要 provenance，使净化后仍可核验来源身份。

净化发布副本不能反向覆盖工作态 manifest，否则会破坏本地复现能力。若相对路径本身含敏感信息，也应重写为发布包内的中性路径或置空。

## 行为证据检查

交付报告至少概括：

- 评测臂、任务族与 holdout 设计；
- 相对 no-skill 的实际改善；
- 重蒸馏时相对 old-skill 的胜负与保留项；
- 兄弟路由诱饵表现；
- 机械断言、关键失败和残余风险；
- 评测泄漏、样本不足或运行环境差异。

不要只给一个平均分。对高风险失败、错误路由和无依据计算单独披露。

## 版本、回滚与变更范围

- 为交付物记录可比较的版本或内容指纹；
- 保留上一可用版本，直到新版本被接受；
- 记录新增、删除、合并、重命名和 supersedes lineage；
- 从 canonical bundle 生成的产物应先进入 staging 并通过校验，再以可回滚方式替换；
- 若目标位置相对上次交付指纹存在人工修改，先报告差异并决定回灌或保留，不能静默覆盖；
- 不在未授权情况下安装到全局位置、发布到市场、推送远程或覆盖生产版本；
- 若用户只要求审计或候选输出，到此交付报告即可，不扩大为部署工作。

## 最终交付说明

面向用户的说明应简洁但可核验，包含：

1. 交付了哪些能力和文件；
2. 与旧版本相比的主要行为变化（如适用）；
3. 运行了哪些验证，结果是什么；
4. 哪些限制或风险仍存在；
5. 用户若要安装、替换、发布或扩大试点，需要采取什么下一步。

内部过程细节可以放在审计报告，不要求用户阅读所有方法论文档才能使用 skill。

## 交付前停止条件

出现以下任一情况时，不应标记为 ready：

- 核心主张无法回到原始来源；
- 关键输出契约或兄弟路由仍不稳定；
- 新 skill 未显示相对 no-skill 的实际增益；
- 重蒸馏结果在关键场景显著退化且未解决；
- 高风险机械断言失败；
- 发布 manifest 未设置 `local_paths_redacted: true`，或任何发布产物仍含本机绝对路径；
- 所需权限、当前数据、专业复核或法域信息缺失；
- 为通过测试泄漏或修改了 holdout，却没有新的独立复测。
