# 阶段 2 — 构造可执行 skill

## 目标

把 promotion gate 通过的能力构造成适合目标运行环境的 skill 包。RIA（原文、解释、应用）可以作为蒸馏者的分析检查，但不要求在最终入口中机械保留固定六段。最终结构服从可发现性、执行可靠性和渐进披露。

## Canonical capability 与运行入口

先为每项保留能力建立 canonical capability card，保存稳定 capability ID、selection 理由、来源证据、RIA 分析、执行契约、边界、关系和编译去向。书级 capability bundle 记录这些 cards、router 与 promotion 状态。运行时的 SKILL.md 或 router 是从该能力模型编译出的热路径，不应成为唯一证据仓库。

Card 可以比运行入口详细，因为它只在审计、来源核对或边界任务时按需读取。修改执行规则时同步更新 canonical card 和编译产物，避免两套互相矛盾的事实源。

从 bundle 编译出的目录视为生成物：内容变更应先回到 canonical card/bundle，再重新编译。记录生成物指纹，发现人工修改时停止并让维护者选择回灌、保留或放弃差异，不能静默覆盖。

## 三层信息架构

### 第 1 层：name 与 description

这是发现和路由层，应简短且有区分度：

- name 表达能力，不照搬书名或抽象口号；
- description 说明它完成什么，以及什么任务状态下适用；
- 只有能防止常见误路由时才加入关键排除项；
- 不把所有步骤、来源背景、案例和边界塞进 description；
- 不依赖某个模型品牌或编排器名称。

先与最相近的兄弟 skill 对比，再写 description。若两个 description 对同一用户请求都同样合理，应先调整能力边界。

### 第 2 层：SKILL.md 入口

入口只保留完成多数请求需要的内容：

- 目的和适用范围；
- 最小执行契约；
- 真实的安全、权限和质量约束；
- 何时停止、询问或转交；
- 指向条件性 references、scripts 或 assets 的路由说明。

短 skill 可以完全自包含。只有当条件性细节确实会占用无关上下文时才拆支持文件，不为目录整齐创建空资源。

### 第 3 层：按需支持资源

适合放入支持文件的内容包括：

- 只在某一模式、行业、法域或交付格式下需要的程序；
- 大型术语表、来源证据账本、完整案例库和反例库；
- 公式、数据字典、输入输出 schema 和机械验证规则；
- 可重复且确定性强的处理脚本；
- 生成结果需要复制或改造的资产。

入口必须说明何时读取或运行每个资源。相同规则只维护一份，不在入口和 references 重复粘贴。

## 把来源分析转成执行契约

| 蒸馏材料 | 最终用途 |
|---|---|
| Reading / 原始证据 | 支撑来源忠实度和审计；保留最短必要引用与精确锚点 |
| Interpretation / 综合解释 | 定义方法如何改变决策；标记为综合或推断 |
| Past Application / 书中案例 | 提供机制证据、示例或边界，不自动变成必做步骤 |
| Future Trigger / 未来情境 | 写入可区分的路由条件和真实用户语言 |
| Execution / 执行 | 输入、动作、输出、完成标准、停止和失败路径 |
| Boundary / 边界 | 负例、兄弟路由、失效信号、权限与时效要求 |

不要为了保持 RIA++ 外观重复这些标题。只要上述信息在合适层级可查且不互相矛盾即可。

## 可执行契约的写法

### Trigger

描述任务状态，不只列关键词。例如“用户已有一个重大方案，需要系统查找会推翻方案的失败路径”比“用户需要思考时”更可路由。记录容易误触发的相邻请求，供阶段 3 和阶段 4 使用。

### Inputs

区分：

- 必须输入：缺失时不能可靠执行；
- 可选输入：缺失时可采用明确默认值；
- 可检索输入：只有得到授权且环境具备能力时才能取得；
- 当前事实：若可能过期，必须记录 as-of 或请求更新。

### Procedure

- 只固定真正影响正确性或安全性的顺序；
- 开放式任务写目标、判断标准和候选方法，不伪装成唯一流程；
- 对重复计算、格式转换或校验优先使用可验证脚本；
- 不把“认真分析”“保持客观”等泛泛建议当步骤。

### Output 与完成标准

明确可观察的交付物、必要字段和质量断言。完成标准应允许机械检查或评审，不要求固定措辞。

### Stop / Escalate

说明何时：

- 信息不足，需要用户补充；
- 任务超出 skill 边界，应转交兄弟能力；
- 需要新的外部权限或高影响操作；
- 来源、数据或公式不可靠，应停止而不是猜测；
- 已达到交付标准，避免无限扩张任务。

## 来源与推断的呈现

- 每个关键、非显然或高风险规则都应能从稳定 capability ID 追溯到候选 ID 和精确来源锚点；
- 不要求把长篇原文塞入 SKILL.md；可将证据账本放在按需 reference；
- 现代化适配、跨领域推广和工作流设计标为蒸馏者推断，不能冠以作者名义；
- 对来源中的矛盾、例外和低置信度 OCR 保留说明；
- 引用遵循许可和合理引用原则，以核对所需的最短片段为限。

## 平台与权限可移植性

- 用“读取文件”“调用可用检索能力”“运行确定性校验”等能力描述，不假定某个专有工具名称；
- 若目标平台不支持自定义 frontmatter，把来源和 lineage 放在正文或 manifest，不以静默丢失为代价；
- 不让 skill 声称拥有用户未授予的网络、写入、发布或交易权限；
- 将本地约定与普遍要求分开，避免把一次项目偏好固化为所有环境的硬规则。

## 构造顺序

1. 从 promotion 记录写一段能力与路由定义；
2. 写最小执行契约，先验证任务能闭环；
3. 只增加能改变执行决定的来源规则、边界和例外；
4. 把条件性细节移动到有明确路由的支持文件；
5. 建立 candidate → capability → skill/resource 的 lineage；
6. 用少量 dev cases 检查是否可执行，再进入 portfolio 链接和正式评测。

## 自检

- 入口是否比原书摘要更像一个执行说明，而不是读后感？
- description 是否能与兄弟 skill 区分，而没有吸引无关请求？
- 每项硬性规则是否确有正确性、安全或权限理由？
- 一般能力是否被不必要地写死为固定步骤、固定数量或固定工具？
- 条件性内容是否按需披露，且入口能找到它？
- 输出、停止条件和失败路径是否可观察？
- 证据、综合和推断是否清楚分开？
