# 有限预算、托管、检查点与恢复

## R01 [原则] 预算先于启动

分别登记资源可用期、阶段累计 wall-time、单应用上限、物理目标时钟和带时区的绝对截止。资源仍可用不等于预算无限；预算上限不等于保证完成时间。

账本最少字段：`case / stage / attempt / source_id / source_clock / settings / backend / started_at / absolute_deadline / cumulative_cost / unique_progress / last_checkpoint / exit_status / updated_at`。
失败、重载、重算、IO均计成本；改名、重启或换执行者不清零。延期仅在用户明确或条件预授权范围内，启动前追加理由、增量、已耗和新截止；不静默改旧记录。
[案例] 某项目采用每应用不超过一天的上限；这不是 STAR 软件限制，也不是新任务自动获得的一天许可。本 skill 不设数字默认。

## R02 [原则+可选策略] 串行托管与控制权

- 每个受控任务有唯一执行责任人，使用明确命名的受控脚本、任务调度器或持久会话；SSH断开不表示求解结束。
- 资源未知或项目要求串行时，按“预检→原生小段→保存→下一阶段”排队，锁的范围与实际资源对应。
- **单 STAR 是一种项目资源/许可证策略，不是普适禁止并行。** 允许并行时先确认用户scope、模块/并行授权、RAM/显存/CPU亲和与IO余量，隔离输出、锁和进程组；不能借此改变其他任务。
- 用确定性程序低开销监控；模型仅在实际启动、阶段结束、异常、决策/用户查询时分析，不按步或每轮反复扫描。
- 先读driver状态，再核新鲜原生心跳、时钟、退出与进程身份；旧 `running` 和旧进程号不是活性证据。控制前重新确认归属。

## R03 [原则] 正常停止与可恢复点

优先已核验的协作停止/保存，确认完整健康时间步和保存完成。强制超时只针对明确隔离的自有进程组，记录原因；不全局杀进程。

检查点保存源身份、实际时钟和设置元数据；保存节奏结合成本、故障风险和可用预算确定，留当前有效点及有界滚动备份。
文件存在、mtime、传输成功均不单独证明可恢复；用原生加载和语义读回确认。网格生成等阶段不保证能从中途恢复。
不把不完整故障现场命名为“正常检查点”，不热改活应用护栏以掩盖超限。

## R04 [原则] GPU故障恢复先核scope与健康

1. 保全故障事件/日志和最后正常源，安全结束受影响的自有实例并确认资源/锁释放。
2. 查**当前用户对该节点、该任务、该类故障的恢复授权**。历史其他节点放行或一般自主推进不是本次恢复许可。
3. 在有明确时限、计入预算的窗口内，做新鲜只读健康/资源检查：设备可访问，无需未授权reset或维护，无资源冲突/危险内存磁盘状态。
4. 核正常完整checkpoint与剩余预算，确认预期净进展值得继续；在获准的恢复应用实际加载时核源时钟、设置与后端，不默认另开一次验证应用。健康字段缺失、空白或N/A是未知，不等于明确“无需恢复动作”，须按设备文档与当前恢复策略处理。
5. 满足全部条件才从正常源按已批准设置续算，另立attempt并记失败、重算、恢复次数和新增正常进展。

无净进展、反复近似故障、源不确定、设备需维护、新严重错误或其他用户冲突时停止盲试并上报。数值非finite、IO、实现故障不自动归类为瞬态GPU故障。
GPU错误码本身不证明OOM或硬件坏；只使用与自有任务有关的可获日志，不擅自reset、重启、改驱动/MPS/时钟/精度或停止他人应用。
**不提供无限重试，也不把某案例的“无固定两次上限”推广成通用恢复授权。**

## R05 [原则+谱系策略] 分支不交错

恢复谱系记录 `parent_source → attempt → accepted_normal_checkpoint`，失败现场和原始数据另存且标记状态。

对于“同一轨迹从正常checkpoint回滚续算”的策略，选中恢复分支后，由它整体替换选定checkpoint之后的旧失败尾段；边界重复点按预先规则只取一次，不只覆盖同timestamp再交错残留旧尾。保留原始两条分支供追溯。

这不是要求所有研究分支合成一条线：独立重复、参数比较和不同源的轨迹必须分别分析。并行资源许可与数据谱系有效性是两件事。
同源比较也只是控制初态的可选设计；若采用，两个分支分别从冻结原源开始，不让后一分支继承前一尾段，然后独立检查过渡与成熟度。
